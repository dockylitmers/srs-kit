# SRS (srs-kit)

고객사와 합의한 범위 기준선으로 SRS를 쓰고 관리한다. 판정 규칙은 하나다: **확인된 SRS와 다르면 버그, 없으면 변경 요청.**

- 키트 위치: `$SRS_KIT`. 비어 있으면 `~/.claude/skills/srs` 링크가 가리키는 폴더의 상위 폴더. 도구: `$SRS_KIT/bin/srs` (Node.js 18+, 의존성 없음).
- 기준: `$SRS_KIT/STANDARD.md`(쓰는 법, 기준 버전은 그 파일 맨 위), `$SRS_KIT/PROCESS.md`(순서). 작업 전에 해당 절을 읽는다.
- 템플릿: `$SRS_KIT/templates/` (페이지, 예시 기능, 고객사 메시지, 작업 세션 지시서: 내용 작성·구현 대조·사전 답변·독립 검토·번역·사이트).
- 문서 사이트: `$SRS_KIT/SITE.md`(사이트가 갖출 것). 사이트 코드가 있으면 `$SRS_KIT/web/README.md`(공개본에는 `web/`이 없을 수 있다. 그때는 SITE.md대로 만든다).

## 온보딩 ("SRS 온보딩", "SRS 시작", "SRS 온보딩 이어서")

Claude Code 첫 실행처럼 **한 번에 하나씩** 묻는다. 질문은 한두 줄, 기본값을 붙이고, 답을 받으면 바로 다음으로 간다. 터미널에서 혼자 하려는 사람에게는 `srs onboard`를 알려 준다(같은 질문을 하고 같은 출처 목록에 넣는다).

1. **상태 보기.** `srs.config.json`과 출처 목록이 있으면 세팅을 건너뛰고 `srs source list --unread`로 읽기 전 출처를 보여 준 뒤 3단계로 간다.
2. **기본 정보**(없을 때만). 프로젝트 이름(기본: 폴더 이름)을 묻고 `srs init . --name "<이름>"`. 예시 페이지는 묻지 않는다(`--example`은 처음 써 보는 사람이 원할 때만).
3. **근거 문서 받기.** 이렇게 묻는다:
   > 근거 문서가 있으면 링크나 파일 경로를 붙여 넣어 주세요. 여러 개를 한 번에 붙여 넣어도 됩니다.
   > Notion 페이지·데이터베이스, Google 문서·드라이브 폴더, PDF·Word·한글·엑셀 파일, Figma, 이슈 링크, 문서가 든 폴더, "고객사 메신저 대화 9월분" 같은 메모도 됩니다. 다 넣었으면 "끝"이라고 해 주세요.
   - 받은 것마다 `srs source add "<위치>" --kind <종류> [--title "<제목>"] [--date YYYY-MM-DD]`. Notion 최상위 페이지·데이터베이스와 드라이브 폴더는 `--group`, 로컬 폴더는 `--each`. 종류는 도구가 추정하므로 계약 자료인지처럼 **애매한 것만** 묻는다.
   - 파일은 넣을 때 지문이 기록된다. 읽은 판을 남길 사본(`--copy`, 보관함 `srs-sources/<ID>/`)은 파일이 있을 때 한 번만 묻고 기본은 둔다. 보관함은 git에 올라가지 않으니 계약서도 된다. 원본이 저장소 안에 있고 git이 무시하지 않는다는 경고가 나오면 그대로 전한다.
   - Notion 등 링크는 읽을 때 문서의 마지막 수정일을 보고 `--edited YYYY-MM-DD`로 넣는다(나중에 바뀌었는지 비교하는 기준).
   - 넣은 결과를 ID·종류·제목 표로 보여 주고 "더 있나요?"를 한 번 묻는다. 계약 자료(순위 1)가 하나도 없으면 "계약서나 계약에 붙은 제안서·범위표가 있나요? 범위의 첫 번째 근거입니다."를 꼭 묻는다.
4. **읽기.** 읽기 전 출처를 순위 순서(계약 → 고객사 답 → 화면 → 팀 결정)로 연다.

   | 출처 | 읽는 법 | 못 열 때 |
   | --- | --- | --- |
   | Notion | Notion 연결(MCP)로 페이지를 가져온다. 하위 페이지, 데이터베이스 행, 댓글, 첨부까지 | 연결이 없으면 `/mcp`로 연결하거나, 페이지를 PDF·Markdown으로 내보내 경로를 달라고 한다 |
   | Google 문서·드라이브 | Google 연결이 있으면 그것으로, 공개 링크면 웹 가져오기 | 파일로 내려받아 경로를 달라고 한다 |
   | PDF | 파일 읽기(긴 문서는 페이지 범위를 나눠) | |
   | Word·엑셀·발표 자료 | 문서 스킬(docx·xlsx·pptx)이나 변환 도구 | 한글(HWP)은 PDF로 저장해 달라고 한다 |
   | 이미지·Figma | 이미지는 파일 읽기, Figma는 Figma 연결 | 연결이 없으면 화면 캡처를 달라고 한다 |
   | 이슈·PR | `gh issue view <번호> --comments` 등 | |
   | 웹 페이지 | 웹 가져오기 | 로그인이 필요하면 PDF로 |
   | 메모 | 내용을 받아 정리하거나, 받을 수 없으면 위치만 남긴다 | |

   - **묶음**은 하위 문서를 모두 열고 문서마다 `srs source add`로 한 행씩 넣는다. 확인 범위 표의 그 묶음 행에 전체 수와 넣은 수를 적는다(같아야 끝).
   - 이슈 본문·코멘트에 걸린 고객 소통 도구 링크도 모아 빠진 것을 넣는다(PROCESS 1단계).
   - 열지 못한 출처는 "확인하지 못한 출처" 표에 이유와 다음 조치를 적고, 출처 행의 반영 위치는 `반영 없음: 열 수 없음`으로 둔다.
   - 비밀값(계정, 비밀번호, API 키)과 개인정보는 옮기지 않는다. 위치와 항목 이름만 적는다.
5. **보고하고 넘어가기.** 사람에게 한 번에 보여 준다: 출처별 한 줄 요약, 출처끼리 엇갈리는 곳과 STANDARD 3절 순위로 따른 쪽, 기능 후보 목록(이름·code 제안), 고객사에 물을 것 후보(3.1절 기준으로 고객사 결정인 것만). 기능 목록을 확인받으면 `srs new feature …`로 페이지를 만들고 PROCESS 2단계(초안)로 간다. 초안에 반영한 출처는 반영 위치를 페이지 링크로 바꾼다. 읽기 전 출처가 남으면 `srs check`가 `source-unread` 경고를 낸다.

## 근거가 바뀌었을 때

- `srs check`의 `source-changed`, 또는 `srs source status --changed`: 파일 내용이 바뀌었거나 폴더에 문서가 늘었다. 바뀐 원본을 다시 읽고(사본이 있으면 보관함의 지난 사본과 비교해 무엇이 바뀌었는지 본다) SRS에 반영할 것을 다음 판 목록에 넣은 뒤 `srs source refresh <ID>`. 폴더는 `srs source refresh <키> --each`가 새 문서를 출처로 넣는다.
- 링크 문서는 도구가 바뀐 것을 알 수 없다. 판을 시작할 때와 고객사 확인 요청 전에 `srs source status`의 링크 행을 열어 지금 수정일이 기록한 수정일보다 늦으면 같은 순서로 다시 읽고 `srs source refresh <ID> --edited <새 수정일>`.
- 보관함 사본은 git에 올리지 않는다. `source-copy-tracked` 오류가 나면 안내대로 `git rm --cached`.

## 세팅 (PROCESS.md 0~2단계)

1. `srs init <저장소> --name "<프로젝트>"` → `docs/srs` 뼈대와 `srs.config.json`. 사이트까지: `web/`이 있으면 `--web <앱 폴더>` 후 `web/README.md`의 "합칠 것", 없으면 `SITE.md`대로 사이트 세션에 맡긴다.
2. 고객사와 합의 방식(확인 요청 위치, 확인 담당, 고객사에 묻는 범위, 댓글 확인 요일·시각, 회신 기한, QA 판정 규칙, 변경 요청 절차)을 정해 `overview`의 "합의 방식"에 적는다. 고객사 발송은 사람이 승인한다.
3. 출처 전수 확인: 고객 소통 도구의 페이지 트리 전체와 이슈 트래커에 걸린 고객 소통 도구 링크를 모두 모아 `baseline/sources`에 한 행씩. 묶음별 전체 수 = 넣은 수.
4. 기능마다 `srs new feature <slug> --title "..." --code ABC`, 여러 기능에 걸친 규칙은 `srs new policy ...`.
5. 출처에 답이 없는 값은 두 페이지만 먼저 "누가 정하나"로 나눠 PM과 기준을 맞춘 뒤 나머지를 나눈다.
6. `srs check` 오류 0.

## 갱신

### 판으로 낼 때 (기본)

1. 고칠 것을 "다음 판 목록"에 쌓는다(페이지, 무엇을, 근거).
2. 기준 커밋을 정한다. 이후 커밋은 다음 판.
3. 목록을 반영한다. 길면 단계마다 패치 파일을 남긴다. 새 규칙 ID가 생기면 `srs sync trace`, 제목이 바뀌면 `srs sync links`, 구현 상태가 바뀌었으면 `srs sync impl`.
4. `srs check --base <기준>` → 오류 0.
5. `srs bump --edition --base <기준> --note "판 요약"` → 바뀐 페이지 전부가 한국어·영어 함께 같은 판 날짜.
6. `baseline/confirmations`의 "판 이력"에 적는다.

### 한 페이지만 급히 고칠 때

1. `srs bump <페이지> --note "바뀐 것 한 줄"` — 고치기 **전에**. 같은 날 두 번째 수정이면 생략.
2. 고친다. 출처를 새로 반영했으면 출처 목록의 반영 위치를 채운다. 새 규칙 ID는 `srs sync trace`로 추적표에 넣는다.
3. 영어: 번역을 고친 뒤 `srs bump <페이지> --lang en`(영어 version = 옮긴 한국어 버전). 두 언어를 함께 고치면 처음부터 `--lang all`.
4. `srs check` → 오류 0, 새 경고는 고치거나 이유를 남긴다.

### 공통

- bump하지 않는 것(형식 변경): 오타, 서식, 깨진 링크, 링크 글자, 페이지 번호, 개발 근거만 바뀐 것.
- 고객사 확인이 필요하면 `status: in-review`, `templates/messages/confirmation-request.md`로 요청 초안. 답을 받으면 답 칸에 `결론: …`, 확인 기록에 행을 넣고, `(제안)`·`(준비 필요)`가 없고 현재 버전 확인 행이 있으면 `status: confirmed`.
- 기준선 이후 고객사가 확인된 내용과 다른 것을 원하면 `baseline/change-requests`에 CR로 등록하고 결정 후에만 고친다.

## 누가 정하나 (STANDARD.md 3.1~3.2절)

- 고객사에 묻는 것은 넷뿐: 돈(가격, 수수료, 환불), 법·약관·개인정보, 고객사 운영(직원, 운영 시간, 계정, 콘텐츠), 고객사가 요청하거나 계약한 것과 다른 범위.
- 그 밖의 구현 세부는 내부 결정: 개발이 추천하고 PM·리드가 정한다. 결정 기록(5순위 출처)을 달고 표시 없이 쓴다. 정책에서 따라 나오는 관리자 화면 규칙도 내부 결정.
- 표시: `(제안)` = 우리가 값을 제안, 고객사가 확정. `(준비 필요)` = 고객사가 만들거나 줘야 함. 영어는 `(proposed)`, `(client to prepare)`. `(준비필요)`, `(제안: …)`로 쓰지 않는다.
- 한 결정은 한 곳에서 한 번 묻는다. 다른 페이지는 "(확인 요청 N)"으로 링크한다. SRS와 고객 소통 도구 양쪽에서 같은 질문을 하지 않는다.
- 확인 요청 번호는 바꾸지 않는다. 지운 질문은 "삭제" 행으로 남기고, 정해진 질문은 답 칸에 `결론: …`. 질문이 없으면 "이 페이지에는 확인할 질문이 없습니다." 한 줄.

## 쓰는 규칙 (요약, 자세히는 STANDARD.md 4~7절)

- 깊이는 위험 기반: 돈·날짜·상태·권한·개인정보는 규칙 표 + 예시 표(경계값). 화면은 캡처. 내부 구현은 "개발 근거"에만.
- 규칙 하나 = 표 한 행 = ID 하나(`<code>-NN`), 출처 ID(`SRC-NNN`)를 단다. 시스템이 알 수 없는 사건을 조건으로 쓰지 않는다.
- 숫자가 있으면 예시, "~하면"에는 "아니면", 형용사 금지, "확인 필요" 대신 고객사 결정이면 `(제안)` + 확인 요청, 내부 결정이면 정한 값.
- 고객사가 읽는 부분: 이슈 번호·진행 상태 열·코드 이름·사람 이름·내부 ID 금지, 쉬운 말(앱 푸시, 문자, 이메일).
- "이번 출시에 없는 것"은 사실만. "추가 개발로 제안", "별도 견적" 같은 영업 문구와 개발 제안은 쓰지 않는다.
- 본문에 `# 제목`·"최종 수정일" 줄 없음. 링크는 상대 경로, 링크 글자 = 대상 페이지 제목. 최상위 이름 `en`, `v` 금지. `docs/srs` 안에 작성 안내 문서를 두지 않는다(메모는 MDX 주석).
- 페이지 번호를 쓰면(설정 `numbering`) 제목 번호 = 개요 표 번호 = 규칙 ID 접두어. ID는 다시 매기지 않는다.
- 영어: 화면 문구는 `"한국어" (English)`, 표시·절 이름은 STANDARD.md 7절 고정 번역. `templates/briefs/translate.md`.
- 비밀값·개인정보는 옮기지 않는다. 예전 버전 파일(`docs/srs-versions/**`)은 고치지 않는다.

## 검수

1. `srs check` (CI나 커밋 전에는 `srs check --strict`, 판이면 `--base <기준>`, 기준선 파일이 있으면 `--baseline`). 결과를 오류·경고 유형별 개수로 보고한다. 기준선으로 숨긴 수와 없어진 수도 함께.
2. `srs status`로 페이지별 버전·번역·상태·`(제안)` 수·마지막 확인 버전을 본다.
3. 고객사에 보내기 전에는 새 문맥의 검토자에게 맡긴다(`templates/briefs/review.md`). 코드와 결정 기록에 대조한다.
4. 사람이 보는 것(STANDARD.md 10절):
   - 고객사 담당자가 이 페이지만 읽고 규칙마다 맞다/틀리다로 답할 수 있다.
   - 확인 요청이 고객사가 정할 것에만 있고, `(제안)`이 맞는 행에 근거와 함께 붙었다.
   - 사람 이름, 내부 ID, 낡은 개발 근거, 영어의 옛 메뉴 이름이 없다.
   - "이번 출시에 없는 것"이 고객사가 기대할 만한 것을 사실로만 다룬다.
   - 예시 값이 실제 운영 값이다(목업·테스트 값 아님). 캡처가 최신 빌드다.
   - 이슈·회의에서 정한 것이 모두 반영됐다.

## 하지 않는 것

- 승인 없이 고객사·팀 채널에 보내거나 이슈 트래커에 쓰지 않는다. 초안까지만 만든다.
- 구현 세부를 고객사에 묻지 않는다. 내부 결정으로 PM·리드에게 올린다.
- 코드가 SRS와 다르다고 SRS를 코드에 맞춰 몰래 고치지 않는다. 차이는 구현 상태에 적고 SRS 고침 / 코드가 틀림(버그) / 고객사 확인 / 변경 없음 중 하나로 정리한다.
- 확인된 페이지를 bump 없이 고치지 않는다(형식 변경 제외).
