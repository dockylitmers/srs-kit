# 지시서: SRS 구현 대조 세션 (읽기 전용)

`[ ]`를 채워 작업 세션에 그대로 준다. 기준은 srs-kit PROCESS.md 3단계다.

## 목표
`docs/srs`의 모든 규칙 ID를 현재 코드와 대조하고, SRS에 없는 구현을 모두 찾는다.

## 기준
- 브랜치·커밋: [브랜치] 최신. 확인한 커밋 SHA를 보고서 맨 위에 적는다. 대조 중 새 변경이 들어오면 기준을 옮기지 않고 따로 적는다.
- 근거로 쓰는 것: 앱 코드, DB 스키마, 기술 스펙, 이슈·PR(읽기만).

## 할 일
1. 규칙 ID마다 상태: 구현됨 / 다르게 구현됨(무엇이 다른지 한 줄) / 미구현 / 범위에서 빠짐(근거).
2. SRS에 없는데 구현됐거나 이슈에서 결정된 기능: 들어갈 SRS 페이지(없으면 새 페이지 이름 제안)와 핵심 규칙·실제 값.
3. 돈·날짜·상태·권한·개인정보 규칙은 코드의 실제 값을 그대로 옮긴다.
4. 제품 정책 판단이 필요한 것은 추측하지 않고 "결정 필요"로 적는다.

## 보고서 형식 (규칙 ID가 열쇠)
1. 기준 커밋, 확인 일시, 상태별 개수, SRS에 없는 기능 수, 규칙 ID 개수 대조(SRS의 ID 수 = 표의 행 수)
2. `| 규칙 ID | SRS 요약 | 현재 구현 | 상태 | 근거 |`
3. `| 기능 | 들어갈 페이지 | 핵심 규칙과 실제 값 | 근거 |`
4. 결정과 구현이 다른 것, 결정 필요
5. 확인하지 못한 것과 이유

## 금지
- 코드·`docs/srs`·스펙 수정, 커밋, push, PR.
- 이슈 트래커 쓰기, 고객사·팀 채널 발송.
