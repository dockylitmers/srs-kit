# 지시서: SRS 구현 대조 세션 (읽기 전용)

`[ ]`를 채워 작업 세션에 그대로 준다. 기준은 srs-kit PROCESS.md 3단계다.

## 목표
`docs/srs`의 모든 규칙 ID를 현재 코드와 대조하고, SRS에 없는 구현을 모두 찾는다.

## 기준
- 브랜치·커밋: [브랜치] 최신. 확인한 커밋 SHA를 보고서 맨 위에 적는다. 대조 중 새 변경이 들어오면 기준을 옮기지 않고 따로 적는다.
- 근거로 쓰는 것: 앱 코드, DB 스키마, 기술 스펙, 이슈·PR(읽기만).
- 기술 스펙은 구현보다 뒤처질 수 있다. 메인 스펙만 보지 말고 진행 중인 스펙 변경, 최근 병합된 PR, 코드까지 대조한다.

## 할 일
1. 규칙 ID마다 상태: 구현됨 / 다르게 구현됨(무엇이 다른지 한 줄) / 미구현 / 범위에서 빠짐(근거).
2. SRS에 없는데 구현됐거나 이슈에서 결정된 기능: 들어갈 SRS 페이지(없으면 새 페이지 이름 제안)와 핵심 규칙·실제 값.
3. 돈·날짜·상태·권한·개인정보 규칙은 코드의 실제 값을 그대로 옮긴다.
4. 다르게 구현됨과 SRS에 없는 구현은 행마다 처리 제안을 넷 중 하나로 단다(STANDARD 9절 "구현과 다를 때").
   - **SRS 고침**: 구현이 맞고 내부 결정 대상이다.
   - **코드가 틀림(버그)**: SRS가 맞다.
   - **고객사 확인**: 고객사가 정할 항목(돈, 법·약관·개인정보, 고객사 운영, 요청과 다른 범위)이다. 고객사가 볼 수 있는 동작을 고객사와 합의 없이 바꿨으면 이미 만들었어도 여기다.
   - **변경 없음**: 표현만 다르고 동작은 같다.
   어느 것인지 판단이 안 서면 추측하지 않고 "결정 필요"로 적는다.
5. 모든 페이지의 "개발 근거"를 코드와 맞춰 보고, 낡은 경로·설명을 목록으로 낸다.

## 보고서 형식 (규칙 ID가 열쇠)
1. 기준 커밋, 확인 일시, 상태별 개수, SRS에 없는 기능 수, 규칙 ID 개수 대조(SRS의 ID 수 = 표의 행 수)
2. `| 규칙 ID | SRS 요약 | 현재 구현 | 상태 | 처리 제안 | 근거 |` (처리 제안: SRS 고침 / 코드가 틀림(버그) / 고객사 확인 / 변경 없음)
   - 상태 칸은 넷 중 하나만 쓴다: 구현됨 / 다르게 구현됨 / 미구현 / 범위에서 빠짐. 내용 작성 세션이 `srs sync impl --from <이 보고서>`로 추적표와 구현 상태 페이지에 옮긴다. "일부 구현" 같은 다른 말은 건너뛰므로 다르게 구현됨으로 쓰고 현재 구현 칸에 무엇이 빠졌는지 적는다.
   - 한 행에 규칙 ID 하나. 같은 결과면 `CAN-03, CAN-04`처럼 쉼표로 묶어도 된다.
3. `| 기능 | 들어갈 페이지 | 핵심 규칙과 실제 값 | 처리 제안 | 근거 |`
4. 결정과 구현이 다른 것, 결정 필요
5. 낡은 개발 근거: `| 페이지 | 지금 쓴 것 | 지금 코드 |`
6. 확인하지 못한 것과 이유

## 금지

- 이슈 트래커 쓰기, 고객사·팀 채널 발송.
