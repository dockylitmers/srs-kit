# 지시서: SRS 내용 작성 세션

`[ ]`를 채워 작업 세션에 그대로 준다. 기준은 srs-kit의 STANDARD.md와 PROCESS.md 1·2·4·6단계다.

## 목표
[프로젝트 이름]의 SRS를 `docs/srs`에 작성·갱신한다. 고객사가 기능별로 확인할 수 있는 수준까지 쓴다.

## 입력
- 고객 소통 도구: [주소] (전체 문서 수: [N])
- 계약 자료: [위치]
- 이슈 트래커의 결정 코멘트: [검색 조건]
- 구현 대조 보고서: [경로] (있으면)

## 할 일
1. 출처 전수 확인: 고객 소통 도구의 페이지 트리를 하나도 빼지 않고 열어 `baseline/sources`에 넣는다. 이슈 트래커 본문·코멘트에 걸린 고객 소통 도구 링크도 모두 모아 대조한다(이슈에서만 링크된 문서가 많다). 묶음별 전체 수와 넣은 수를 "확인 범위"에 적는다.
2. 기능·정책 페이지 작성: `srs new feature|policy`로 만들고 STANDARD 5~6절대로 채운다. 고객사가 읽는 부분에는 이슈 번호·진행 상태·코드 이름·사람 이름·내부 ID를 넣지 않고 쉬운 말을 쓴다.
3. 출처에 답이 없는 값은 누가 정하는지 나눈다(STANDARD 3.1절).
   - 먼저 [페이지 두 개]만 나눠 보고서로 내고, PM과 기준을 맞춘 뒤 나머지를 나눈다.
   - 고객사가 정할 것(돈, 법·약관·개인정보, 고객사 운영, 요청과 다른 범위): `(제안)` 또는 `(준비 필요)`와 확인 요청.
   - 내부 결정: 개발 추천값을 "내부 결정 목록"에 올린다. PM·리드가 정하면 결정 기록을 출처로 달아 표시 없이 쓴다.
   - 한 결정은 한 페이지에서만 묻고, 다른 페이지는 "(확인 요청 N)"으로 링크한다.
4. 출처마다 반영 위치를 채운다.
5. 구현 대조 보고서가 있으면 추적표(`srs sync trace`)와 `baseline/implementation-status`에 옮긴다.
6. 판으로 낸다: 기준 커밋 [SHA]. 길면 단계마다 패치 파일을 [경로]에 남긴다. 끝나면 `srs check --base [SHA]` 오류 0, `srs bump --edition --base [SHA] --note "…"`. 한 페이지만 급히 고칠 때는 고치기 전에 `srs bump <페이지>`.

## 완료 조건
- 출처 목록의 묶음별 수가 전체 수와 같다.
- `srs check` 오류 0. 남은 경고는 보고서에 이유와 함께 적는다.
- 확인 요청이 고객사가 정할 것에만 있고, 사전 답변 목록(templates/briefs/pre-answer.md 형식)이 페이지 묶음별로 있다.
- 고객사 확인 요청 초안(templates/messages/confirmation-request.md 형식)이 페이지 묶음별로 있다. 발송 전 독립 검토(templates/briefs/review.md)를 받는다.

## 금지
- 고객사·팀 채널 발송, 이슈 트래커 쓰기, 커밋·push (승인 권한자가 한다).
- 비밀값·개인정보를 SRS나 보고서에 옮기기.
- 코드 수정.

## 산출물
- `docs/srs`의 변경(미커밋), 보고서 [경로]: 한 일, 확인하지 못한 출처, 확인 요청 목록, 내부 결정 목록(PM이 정할 것), 남은 경고.
