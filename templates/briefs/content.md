# 지시서: SRS 내용 작성 세션

`[ ]`를 채워 작업 세션에 그대로 준다. 기준은 srs-kit의 STANDARD.md와 PROCESS.md 1·2·4·6단계다.

## 목표
[프로젝트 이름]의 SRS를 `docs/srs`에 작성·갱신한다. 고객사가 기능별로 확인할 수 있는 수준까지 쓴다.

## 입력
- 고객 소통 도구: [주소] (전체 문서 수: [N])
- 계약 자료: [위치]
- 이슈 트래커의 결정 코멘트: [검색 조건]
- 구현 대조 보고서: [경로] (있으면)

## 할 일
1. 출처 전수 확인: 고객 소통 도구의 문서를 하나도 빼지 않고 열어 `baseline/sources`에 넣는다. 묶음별 전체 수와 넣은 수를 "확인 범위"에 적는다.
2. 기능·정책 페이지 작성: `srs new feature|policy`로 만들고 STANDARD 5~6절대로 채운다. 출처에 답이 없는 값은 (제안)과 확인 요청.
3. 출처마다 반영 위치를 채운다.
4. 구현 대조 보고서가 있으면 추적표와 `baseline/implementation-status`에 옮긴다.
5. 페이지를 고치기 전에 `srs bump`. 끝나면 `srs check` 오류 0.

## 완료 조건
- 출처 목록의 묶음별 수가 전체 수와 같다.
- `srs check` 오류 0. 남은 경고는 보고서에 이유와 함께 적는다.
- 고객사 확인 요청 초안(templates/messages/confirmation-request.md 형식)이 페이지 묶음별로 있다.

## 금지
- 고객사·팀 채널 발송, 이슈 트래커 쓰기, 커밋·push (승인 권한자가 한다).
- 비밀값·개인정보를 SRS나 보고서에 옮기기.
- 코드 수정.

## 산출물
- `docs/srs`의 변경(미커밋), 보고서 [경로]: 한 일, 확인하지 못한 출처, 확인 요청 목록, 남은 경고.
